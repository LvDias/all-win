## C§1 Code entry: `CodeInput`, `CodeChallenge`

### C§1.1 `CodeInput`

**Purpose:** type or paste a one-time code (sign-in, sign-up, step-up, channel change). Base: shadcn `InputOTP` (the `input-otp` library), wrapped in `shared/ui`. If the installed version cannot meet the rules below (paste normalization, alphabet), the Frontend builds the same behavior on a single `<input>`; the visual and accessibility contract does not change.

**Format is open (U16).** The default design is **8 uppercase alphanumeric characters without ambiguous ones**. The component therefore takes configuration, not constants:

| Prop | Default | Notes |
|---|---|---|
| `length` | from Core config (8) | Never hard-coded in a feature |
| `alphabet` | `A–Z 0–9` (superset) | Used only to filter typed characters; the Core is the judge. A case-sensitive format 2 would need a `caseSensitive` prop and a different normalization |
| `groupSize` | 4 | Visual grouping only (`ABCD EFGH`); not part of the value |
| `onComplete(code)` | — | Called once when `length` characters are present |
| `disabled`, `readOnly`, `invalid` | | `invalid` sets `aria-invalid` and the error border |
| `describedBy` | | id of help and error text |

**Structure**
- **One underlying text input** (not one input per slot). Visually: `length` slots in groups separated by a gap (a `–` glyph with `aria-hidden`). Slots are decoration over the single input: the whole area is one tap target.
- Slot: Geist Mono, `text-2xl`, uppercase, height 48 px (≥ 44 px), width flexible 28–40 px so that 8 slots plus the gap fit in a 288 px content width (320 px viewport). Border `--input`, active slot ring `--ring` (2 px), error `--destructive`. The caret is a visible bar in the active slot; under `prefers-reduced-motion` it does not blink.
- No masking: the code is typed from another app and must be checkable. It is not logged, not stored, and the field is cleared after every attempt.

**Input rules**
1. Attributes: `type="text"`, `inputMode="text"`, `autocomplete="one-time-code"`, `autocapitalize="characters"`, `autocorrect="off"`, `spellCheck=false`, `enterKeyHint="done"`, accessible name from a visible `Label` ("Código de verificação" / "Verification code") that also states the length ("8 caracteres").
2. **Normalization on every change and on paste:** remove spaces, hyphens and other separators, uppercase, drop characters outside `alphabet`, truncate to `length`. Pasting `abcd-efgh ` or a whole sentence containing the code gives the same result. (The Core also ignores case and surrounding spaces, S3 AC-5 assumption; this is only convenience.)
3. **The client does not map look-alikes.** The Core decodes `O→0`, `I/L→1` for the recommended format (policy §2.1) and rejects the rest; mapping here too would duplicate a rule that depends on the still-open format (U16). The component only strips separators, uppercases, filters the alphabet superset `A–Z 0–9` and limits the length.
4. **Autofill:** `one-time-code` lets iOS suggest codes from Mail and Android/Chrome from supported apps; this is a convenience, not a guarantee. The WebOTP API is for SMS only and is not used. E-mail templates put the code on its own line in large type, so it is easy to select and copy.
5. **Auto-submit** on completion (`onComplete`), once. An explicit submit button always exists next to it. After a failed attempt the field clears, refocuses and re-arms.
6. Backspace deletes one character; arrows move the caret; Home/End work; selecting all and typing replaces. A long-press paste on mobile works.
7. Field is `readOnly` (not `disabled`) while submitting, so focus and the announced value are not lost.

**Accessibility**
- One focusable control; screen readers announce "Código de verificação, 8 caracteres, campo de texto" and read typed characters as entered. Slots are `aria-hidden` and never receive focus.
- Error text is linked with `aria-describedby`, `aria-invalid=true`, and focus returns to the input after a failure. The error message does not repeat the code.
- Passes WCAG 3.3.8: paste and autofill are allowed; nothing is memorized. Minimum target 44 px. Contrast per F§3 (slot border `--input` ≥ 3 : 1).
- Light and dark reviewed; text resizes to 200 % (slots wrap into two groups on separate lines below 280 px, never overflow).

### C§1.2 States

| State | Visual | Notes |
|---|---|---|
| Empty | slots with `--input` border; first slot active when focused | Placeholder is not used |
| Typing | filled slots show characters | |
| Complete | all filled; auto-submit | |
| Submitting | `readOnly`, slots `--muted` background, spinner in the submit button | |
| Error | `--destructive` border, message under the field | Field cleared |
| Disabled (5 local failures, or 10 min since issue) | `--muted` background, `aria-disabled` | A visible text explains why and what to do; the only action is `Pedir novo código`. The server never reveals exhaustion (policy §3), so this is the UI's own count |

### C§1.3 `CodeChallenge` (composite)

**Purpose:** the same verification block everywhere (S3-02 login, S3-03 sign-up step 2, S3-04 step-up, S3-05 channel change). One component means one behavior to test.

Composition (top to bottom, reading order = DOM order):
1. Description slot (screen supplies the text, including where the code went).
2. `Label` + `CodeInput` + error slot (`role="alert"` only after submit failure).
3. Primary button `Verificar` / `Verify` (spinner while submitting; disabled when incomplete).
4. Resend row: `Reenviar código` / `Resend code` with cooldown (C§1.4) and the info line after a resend: "Enviamos um novo código. O anterior deixou de valer." (a resend replaces the code of its own challenge only). On `deliveryState=failed`: "Não foi possível enviar o código. Tente de novo em instantes."
5. Secondary actions slot (back, use another e-mail, other channel).

Props: `purpose` (`login | signup | step_up | channel_old | channel_new | channel_add`), `onVerify(code)`, `onResend()` (same challenge), `onNewChallenge()` (starts a new one), `cooldownUntil`, `error`, `deliveryState` (`pending | sent | failed`, only for signup / step-up / channel flows; never for `login`), `description`, `secondaryActions`. The component counts its own failed attempts per challenge (not reset by a resend) and, after 5, or after the 10-minute lifetime, locks the input and swaps `Reenviar código` for `Pedir novo código` (`onNewChallenge`). It holds no other business rule; lifetimes, attempts and cooldown values arrive from the Core.

Behavior: polite live region announces "Código enviado" on arrival and "Novo código enviado" after a resend. Errors are announced by the focus move. When locked, the input is disabled, an info line says "Peça um novo código para continuar.", and only `Pedir novo código` remains. Error text is always the single "Código inválido ou expirado. Confira ou peça um novo."

### C§1.4 Resend cooldown and rate-limit wait

- `Reenviar código` is disabled until `cooldownUntil` (from the Core: 60 s today, policy §4; Q33 awaits approval). A new challenge obeys the same cooldown. Label while waiting: "Reenviar em 0:45" / "Resend in 0:45" updated every second **visually**, with `aria-live="off"`; a polite announcement only when it becomes available ("Você já pode reenviar o código").
- On a rate limit the same slot shows "Muitos pedidos. Aguarde {time}." with `Retry-After`; the button stays disabled until then. Under 5 s the text is just the spinner.
- The button uses `aria-disabled` (not `disabled`) so it stays focusable and its reason is readable.
- Clicking while cooling down does nothing and never queues a request. Duplicate sends are impossible by design.
- Under `prefers-reduced-motion` the countdown is text only (no ring or animation).

## C§2 `Stepper`

**Purpose:** show position in a short, linear flow inside a dialog or page (S3-03 two steps, S3-05 four steps, create source, S5 account form). Not for navigation between independent sections (use `Tabs`).

| Prop | Notes |
|---|---|
| `steps[]` | `{ id, label, optional? }`, 2 to 6 steps; steps that do not apply are not in the list |
| `current` | index |
| `variant` | `full` (≥ `md`, in pages or wide dialogs) · `compact` (below `md`, narrow dialogs) |

- **Full:** horizontal `ol`. Each step: circle (number, or `Check` when done) + label. Done: `--status-success` circle with check. Current: `--primary` fill, `aria-current="step"`. Upcoming: `--muted` with `--muted-foreground` text. The connector line is decorative.
- **Compact:** one line "Etapa 2 de 4 · Código do e-mail atual" / "Step 2 of 4 · Current e-mail code" plus a thin segmented bar (`aria-hidden`). Used by default inside `ResponsiveDialog`.
- Steps are **not clickable**; going back uses the screen's own `Voltar` button. Returning to a done step keeps its data in memory.
- Status is never color alone: number/check plus the text "concluída" for screen readers (`<span class="sr-only">`).
- The step title is the dialog's `h2`; on step change, focus moves to that heading and a polite live region reads "Etapa 3 de 4: …".
- Failure in a step stays in that step (inline error); the stepper never shows a failed state of its own.
- Reduced motion: no slide animation between steps; content swaps instantly.

### C§2.1 Form-flow mode (`FormStepper`, rule in F§10.1)

Used when F§10.1 says the create form is long. The `Stepper` above stays the indicator; `FormStepper` is the wrapper that owns the form state, the footer and the review. One shared component, features pass the step list and the step contents.

| Prop | Notes |
|---|---|
| `steps[]` | `{ id, label, optional?, fields[], when? }`; `when` is a predicate on the form state (for example `kind === 'prop'`) and decides whether the step exists |
| `schema` per step | validation run by `Continuar` for that step only; the final button validates all |
| `review` | renders the last step: one group per step with its values and `Editar` |
| `onSubmit` | called once from the review; returns field errors (`pointer`) the wrapper maps to a step |
| `variant` | follows the container: page → `full`/`compact` by breakpoint; dialog → `compact` |

- **State:** one form state (react-hook-form or equivalent, the Frontend chooses) for all steps; unmounted steps keep their values (3.3.7). Gated values are cleared by the feature through `onGateChange(stepId)`, which shows the notice on the later step.
- **Footer:** `Cancelar` (step 1) or `Voltar`, `Pular etapa` (optional steps only), `Continuar`. In the review: `Voltar` and the final action. Sticky on pages; inside the dialog footer on dialogs. Enter in a text field presses `Continuar`; in the review Enter does not submit from a link or `Editar`.
- **Step change:** validate current step → on success move; focus goes to the new step's `h2`; polite live region "Etapa 3 de 5: Conta na plataforma" (C§2). On failure focus the first invalid field of that step; errors summary at ≥ 3 errors (F§10).
- **Review step:** `h2` "Revisar" / "Review"; groups are `section` + `h3` + `dl`; secrets and long texts are shortened with `Mostrar` (F§8). Empty optional groups say "Não definido" / "Not set". `Editar {group}` is a link-styled button; after the user continues from an edited step, the flow returns to the review (F§10.1). Contains any `Alert` that must be read before saving (for example a risk warning) and its acknowledgment control.
- **Back-end errors:** `pointer` → the owning step (`fields[]`) gets the error, focus there, and the review shows "Corrija a etapa {n}" with a link. Non-field errors stay in the review.
- **Dirty guard:** `beforeunload` and the `Descartar alterações?` dialog only while the state differs from the initial one.
- **Small screens:** `compact` stepper, one column, footer buttons full width stacked (`Continuar` on top), safe-area padding (F§9). The review's `dl` stacks term over value.
- **Keys:** `forms.step.progress` ("Etapa {n} de {total}"), `forms.step.done` (sr-only "concluída"), `forms.back`, `forms.continue`, `forms.skip`, `forms.review.title`, `forms.review.edit` ("Editar {group}"), `forms.review.notSet`, `forms.discard.*`; the feature adds its own step titles and review labels.
- **Tests (Frontend/QA):** back/forward keeps values; changing a gating answer clears only dependents and shows the notice; a server `pointer` lands on the right step; a skipped optional step shows "Não definido"; double click on the final button sends once; keyboard-only run through every step; axe on a step and on the review; 320 px reflow.

## C§3 `EmptyState` (variants)

F§10 defines the basic rule (icon, one-sentence title, one-sentence purpose, one primary action, no illustrations). Variants:

| Variant | When | Content |
|---|---|---|
| `first-use` | The user has never created the thing | Icon, title, purpose, primary action. Optional `steps` (numbered `ol`, up to 3, as in S3-10) and an optional help link |
| `filtered` | Filters/search return nothing | Title "Nenhum resultado" / "No results", the active filters as chips, action `Limpar filtros` / `Clear filters`. Never offers "create" |
| `blocked` | The thing cannot exist yet because a prerequisite is missing (for example no account for a route) | Title naming the missing prerequisite, link to create it. Primary action goes to the prerequisite |
| `unavailable` | Data exists but is not shown (permission or dependency not shipped) | Neutral text and no action; never blames the user |
| `history-hidden` | List has only hidden rows (revoked, unpaired) behind a toggle | "Nenhuma fonte ativa." + `Mostrar revogadas` |

Rules: an `EmptyState` is never shown while loading (use `Skeleton`) or on error (use `ErrorState`); it sits inside the same container as the table/cards it replaces, so layout does not jump; the heading level continues the page hierarchy (`h2`/`h3`); the action is a real `Button`/link, never icon-only; the text names the object ("Nenhuma fonte de sinal"), not a generic "Nada aqui".

## C§4 `DataTable` with row actions

**Purpose:** every list screen (sources, connections, invitations, accounts, routes, audit entries). Base: shadcn `Table` (no TanStack Table is required for the first slices; the Frontend may add it by ADR if sorting/virtualization is needed).

**Structure**
- `PageHeader` (title, description, primary action, optional toggle such as `Mostrar revogadas`) → optional filter bar → table/cards → pagination footer.
- Columns: primary identifier first (sticky on horizontal scroll), then state (`StatusBadge`), data, **actions last**. Right-align numbers (`tabular-nums`, F§3.3); left-align text; dates use `DateTimeText`. Header cells `font-medium`, `scope="col"`; the primary cell of each row is `th scope="row"`.
- `caption` (visually hidden) names the table and its count: "Fontes de sinal, 3 itens".
- **Below `md`:** rows become `Card`s (F§9): primary field as title, `StatusBadge` top-right, secondary fields as a definition list in the same order, actions in a kebab. Same data, same actions.

**Row actions**
- One `DropdownMenu` trigger per row: icon button `EllipsisVertical`, 44 px target on touch, accessible name "Ações para {name}" (includes the row name). It is the only per-row tab stop for actions; the primary row link (if any) is a separate one.
- Menu order: non-destructive first (`Renomear`, `Editar`), state changes, then a `Separator`, then destructive items in `--destructive` text with an icon. Destructive items open an `AlertDialog` (F§10); they never act on click.
- Unavailable actions are **omitted**, not disabled, unless explaining why helps (then `aria-disabled` with a tooltip that also opens on focus/tap, and the reason is in the item's text on touch).
- A visible primary action (for example `Gerar código de pareamento`) may appear as a `Button` in the row/card when it is the next step for that state; it is not repeated in the menu.
- After an action that removes or hides the row, focus moves to the next row's trigger (or the table heading when it was the last), and a polite toast confirms. After a rename, focus returns to the row trigger.
- Keyboard: `Enter`/`Space` opens the menu, arrows move, `Esc` closes and restores focus to the trigger.

**Data states** (all inside the same container, F§10)
- Loading: 3–5 skeleton rows matching the column widths. Error: `ErrorState` with retry. Empty: `EmptyState` variants (C§3).
- Live updates (SSE): cell updates do not shift layout; a changed `StatusBadge` text is announced politely only for important states (connection lost, limit state change), never for every tick. A newly arrived row is marked with a `Novo` text badge for 10 s, not color alone. Stale data shows the `Sem dados recentes` indicator (F§7.2).
- Hidden-by-default history (revoked, unpaired) uses a `Switch` in `PageHeader`; the hidden count is announced in the switch's description ("2 revogadas ocultas").

**Sorting and paging**
- Sorting only where it helps; sortable headers are `button`s with `aria-sort`. Default sort is stated in the caption. Date columns sort by instant, never by the formatted string.
- Lists beyond ~50 rows use cursor paging with a `Carregar mais` / `Load more` button and a count ("50 de 132"), not infinite scroll (keyboard and footer reachability). Page size is not user-configurable in V1.
- No row selection or bulk actions until a slice requires them.

**Density:** default row height 48 px (≥ 44 px on touch layouts); `text-sm`. Secondary meta in `text-xs` only when never essential.

## C§5 `RiskBanner` (80 % warning and limit reached)

**Purpose:** make a risk state change impossible to miss while keeping the app calm. Visual language and states come from F§7.1; this component only places them. The Core sends the state and every number (`state`, `used`, `limit`, `percent`, `reason`, `blocked_until`, `enforcement`); the banner never computes or rounds (X-3).

**Where and how many**
- **Account detail / `RiskMeter` area:** one `RiskBanner` per limit that is not `normal`, above the meters.
- **App shell:** at most **one aggregate** banner below the top bar when any account is `warning` or `reached`: "2 contas em alerta, 1 com limite atingido" / "2 accounts in warning, 1 with a limit reached" + `Ver contas` → account list filtered. Severity of the banner = worst state. It lists at most 3 accounts inline, then `+N`. It does not stack per account.
- The banner appears and disappears with the Core state; it is **not dismissible** while the state persists (risk is not noise). It collapses on mobile to a single line with `Ver detalhes`.

**Anatomy:** `Alert`-based. Left: icon (F§7.1). Title (`font-semibold`): state label. Body: limit name, `used / limit` (`MoneyText`), percent (truncated, F§6.2), and the **reason slot**. Footer: link to the account, and for `reached` with enforcement on, the reset time with its zone (F§6.4).

| Core state | Token | Icon | Title pt-BR / en | Body example |
|---|---|---|---|---|
| `warning` | `--status-warning` (soft bg) | `TriangleAlert` | `Alerta (80 %)` / `Warning (80%)` | "Perda diária: US$ 820,00 de US$ 1.000,00 · 82 %" |
| `reached`, enforcement on | `--status-danger` | `OctagonX` | `Limite atingido` / `Limit reached` | "Perda diária: US$ 1.000,00 de US$ 1.000,00 · conta bloqueada até 17:00 (GMT-3)" |
| `reached`, notify only | `--status-danger` | `OctagonX` | `Limite atingido` / `Limit reached` | "… · somente aviso: o bloqueio automático está desativado nesta conta" |
| Daily profit target, notify only | `--status-success` | `CircleCheck` | `Meta atingida` / `Target reached` | "Meta diária: US$ 500,00 de US$ 500,00" |
| Daily profit target, flatten and block | `--status-success` | `Lock` | `Bloqueada até {time}` | "motivo: meta de lucro diária atingida" (F§7.1: a good outcome never looks like a loss) |
| Consistency rule (Q4) | `--status-warning` max | `TriangleAlert` | `Alerta` | Never `reached` |

**Accessibility and live behavior**
- Never color alone: icon, title text and the reason are always present.
- A **state change** is announced once: `warning` and target via a polite live region; `reached` via `role="alert"` (assertive), because trading is affected. Percent ticks inside a state are not announced.
- The banner does not take focus. Its links are in normal tab order; contrast per F§3.2 (strong on soft ≥ 4.5 : 1).
- After a reconnect, the banner shows the refetched state; while data is stale it adds `Sem dados recentes` and never presents the old state as current (F§9).
- The same state always has the same banner in the shell, the account page and the notification (S18); there is no per-screen wording.

**Data this component needs [Dependency S13/S14]:** per limit `state`, `used`, `limit`, `percent`, `reason_code`, `blocked_until`, `enforcement_on`, `kind` (loss/drawdown/profit target/consistency). The shell aggregate needs a Core count by state; the web does not count accounts to decide severity.

## C§6 `NotificationItem`

**Purpose:** one notification, in two places: the bell panel and the list page (S18). One component, two variants, so wording, severity and read state never diverge.

| Variant | Where | Content |
|---|---|---|
| `panel` | `NotificationBell` popover | Compact: severity icon, title, **one-line** body (truncated, full text in the title attribute and the list), account name, relative time, unread dot. The whole row is the link. No secondary action |
| `card` | list page | Severity icon, title, one or two lines of body, account link, absolute date-time with seconds and zone, group count `×3` and "última às {time}", `Nova`/`Não lida` text badge when unread. Actions: `Ver detalhes` (link) and `Marcar como lida` (ghost button; for read items the text "Lida", no action) |

**Data (all from the Core, never computed):** `id`, `severity` (`info | success | warning | danger | critical`), `title`, `body`, `account` (name, `deleted`), `occurred_at`, `count`, `last_at`, `read`, `target_url`.

- **Severity:** tokens and icons per F§7 (`info` `Info` neutral/info · `success` `CircleCheck` · `warning` `TriangleAlert` · `danger` `OctagonX` · `critical` `OctagonX` with a 2 px border and the visible prefix "Crítica"). An sr-only label carries the severity ("Aviso", "Perigo", "Crítica").
- **Unread:** a dot **plus** sr-only "Não lida" (panel) or the visible `Nova` badge (card); read items use `--muted-foreground` for the body, never for the title. Not color alone.
- **Whole-row link without nesting interactive elements:** the title is the link and stretches over the row (`::after` covering the item); the account link and `Marcar como lida` sit above it in the stacking order and keep their own focus rings. Opening the link marks the item read.
- **Time:** relative in the panel ("há 2 min") inside `<time datetime>` with the absolute value in a tooltip that also opens on focus/tap; absolute in the card (F§6.4).
- **Deleted account:** the name followed by "(excluída)", no link.
- **Touch:** row min height 56 px (panel) / actions 44 px (card). Reflows at 320 px; the card's actions wrap below the text.
- **States:** `pending-read` (optimistic dot removal, reverts with a destructive toast on failure); no hover-only information.
- **Never contains:** secrets, webhook URLs (only the source name), or codes.

## C§7 `NotificationBell`

**Purpose:** the single entry point to notifications (there is **no sidebar item**; decided here, Q-S18-7). It lives in the top bar left of the user menu, at every size, so it is one tap or key away from anywhere.

**Trigger:** `Button variant=ghost size=icon` with `Bell`, 44 px target. Accessible name: "Notificações, {n} não lidas" / "Notifications, {n} unread"; with none, "Notificações, nenhuma não lida". The visible badge is `aria-hidden` (the name already carries the number).
- **Badge:** the number as text over the icon (`99+` above 99), hidden at 0. Color by the **worst unread severity**: `critical`/`danger` → `--status-danger` soft, `warning` → `--status-warning` soft, otherwise neutral. The number is the information; the color is secondary. Contrast per F§3.2.
- **Dimmed** (opacity is not used; add the `CircleDashed` micro-icon and the tooltip "Sem dados recentes") while the stream is stale; the count stays but is not presented as current (F§9).

**Panel (≥ `md`):** shadcn `Popover`, non-modal, width 360 px, max height 70 dvh, inner scroll.
- Header: `Notificações` + `Marcar todas como lidas` (disabled when none unread).
- Body: a real `ul` of up to **8** `NotificationItem variant=panel`, ordered **critical first, then unread by time, then read by time**.
- Footer: link `Ver todas` → `/[locale]/notifications`.
- Focus: opens with focus on the first item (or on the header action when the list is empty); `Tab` order is header → items → footer; arrow keys move between items (roving tabindex); `Enter` opens; `Esc` closes and returns focus to the bell.
- States: loading → 3 skeleton rows; error → compact `ErrorState` with `Tentar novamente`; empty → "Nenhuma notificação." and the `Ver todas` link; stale → "Sem dados recentes" line.
- **Below `md`** there is no popover: the bell is a link to the list (a popover over a small screen would cover the list anyway).

**Live behavior**
- The count updates in place. A polite announcement "{n} não lidas" only when the count **increases**, at most once every 5 s, with bursts coalesced ("3 novas notificações").
- A new `critical` item is announced by `CriticalBanner` (assertive) and is **not** announced again by the bell. A new `danger` item shows a destructive `Sonner` toast with `Ver`, 8 s; `warning` and `info` only change the bell. The toast is never the only trace (the item stays in the panel).
- Mark-read changes are not announced.
- After a stream reconnect the bell refetches and applies only newer events (F§9).

**Why bell-only works:** the page is reachable by the bell on every screen, by `Ver todas`, by banner links and by URL; adding a sidebar entry would duplicate the entry and the unread count. If the PO later wants an entry, it is added as a plain sidebar link with no second badge.

## C§8 `CriticalBanner` (variant of `RiskBanner`, S18)

**Purpose:** the maximum alert for events that leave a position or account in an unsafe state (exactly two cases, S18 AC-5 / Q51: **the Q27 orphan-leg flatten, including `sync.bracket_double_fill`**, and **U19, a flatten that failed after cancelling protection and left a position unprotected, from any origin**, including the local enforcement flatten). Everything else is `danger` at most: a disconnect with an open position (`sync.disconnected_in_trade`), a bracket flagged incomplete, and a reactive-block flatten or cancel that fails while the position keeps its protection. An unprotected-bracket or reactive-block producer is critical **only** in the U19 case. It uses the anatomy of `RiskBanner` (C§5) but is driven by **notifications**, not by limit states, and cannot be dismissed until the user has read the item.

**Where:** app shell, directly below the top bar. Shell order when several apply: offline banner (F§10) → `CriticalBanner` → aggregate `RiskBanner`. At most one of each.

**Anatomy:** `Alert` (`--status-danger` soft background, **2 px** border in `--status-danger`), icon `OctagonX`, visible prefix "Alerta crítico:" / "Critical alert:", title from the Core, account name, time. Action: `Ver detalhes` (link to the item's target, which marks it read). Several unread: "{n} alertas críticos não lidos" / "{n} unread critical alerts" + `Ver` → the notification list (critical first, unread filter).
- **No close button, no `Agora não`.** It disappears only when every critical item is read. Reading acknowledges that the user saw it; it never resolves the underlying state, and the banner text never implies it did. The banner offers no acknowledge shortcut: the item is read by opening it (or by `Marcar como lida` in the list), so the user sees the detail first.
- **No resync, reopen or unblock controls here** (S11 AC-2, S15 AC-3): the link goes to the account page where those controls live.
- Wording is the notification's own text, identical in the shell, the account page and the list (C§5 rule).

**Accessibility and live behavior**
- A critical item that **arrives live** is announced once with `role="alert"`. On a full page load with items already unread, the banner is a labelled region (`role="region"`, name "Alertas críticos") and is **not** re-announced assertively on every load.
- It does not take focus. Links are in the normal tab order, right after the top bar. Contrast per F§3.2; severity is icon + prefix text, not color.
- **Sticky under the top bar** while its height is under 20 dvh; when the viewport is short or the user zooms to 200 %+ (reflow), it becomes static so it never obscures focused content (WCAG 2.4.11). Scroll padding accounts for it.
- Mobile: prefix, title and the single action on at most two lines; the action is ≥ 44 px.
- Reduced motion: appears without slide animation.
- After reconnect it shows the refetched unread set; while stale it adds `Sem dados recentes`.

**Data this component needs [Dependency S18]:** `severity = critical`, `read`, `target_url` per notification and the unread critical count.
