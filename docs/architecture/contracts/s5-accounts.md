## 2. Decisions

1. **Update is `PUT` with full replacement, not `PATCH`.** Step-up operations must be POST or PUT, because the proof travels in the body (2.0.0). The edit form already sends every field, so full replacement is also simpler to validate than partial `if/then` rules: an absent `binding` unbinds, and an absent `multiplier` means 1.
2. **Create idempotency by `Idempotency-Key`, ids generated by the Core.** No client-generated ids (Esquadro, 2.0.0).
   - Replaying the same key and body within 24 h (`step_up` ignored) returns 200 with the account as it is now. If the account was archived since, the replay returns it with `archived_at`; this is the only read that shows an archived account.
   - A key is never released (`UNIQUE (user_id, create_idempotency_key)` never expires). The same key with a different body, or after 24 h, gets 409 `accounts.idempotency_key_reused`, so a key never creates a second account.
   - Only a success consumes the key, so the retry after a step-up works.
3. **Binding by natural key** `{connection_id, platform_account}` (`UNIQUE (connection_id, platform_account)` in `gateway.venue_account`). `VisibleAccount` does not change. Its `account_id` plus the account list give the "already bound to {name}" text without another call.
4. **Prop selection:** either `preset_version_id` (+ `firm_platform`) or the four manual fields `firm_name`, `plan_name`, `phase`, `size_amount`. Manual mode covers the time before S16 (Q40) and the plans that are excluded from presets (S16 AC-9). With a preset, firm, plan, phase and size come from the preset version.
5. **Generic rule version (provisional, Q40):** a prop account without a preset uses a global generic rule version per kind (`RuleVersion.is_generic`, stance `unknown`, no quotes). Its choice is required (Q25), and `rule_version_id` keeps naming the rule the user saw, so the data-model invariant "a choice always names the rule seen" holds before S16.
6. **`OptInState` changes (2.1.0, now owned by `modules/accounts.yaml`):**
   - `firm_stance` and `current_rule_version_id` are optional (absent only for real accounts);
   - new `pending_reason` ∈ `stance_changed` / `text_changed` / `preset_attached`, required exactly with `pending_review` (Q26, Q42, Q41).
   - These are additive on the wire for every state that existed before, except real accounts, which no longer get a meaningless `firm_stance`. Nothing is implemented against it yet.
7. **Q-S5-12 — copy opt-in of an account that is not a follower: `state = not_required`.** It means "no choice is asked now". `firm_stance` is still reported, so the S7 follower picker knows a choice will be needed. `setAccountOptIn(kind=copy)` on such an account gets 422 `accounts.opt_in_not_applicable`. The copy choice is made atomically when the account is added as a follower (S7/S19, `account_opt_in_accept`, target = follower).
8. **Q42 — material text change:** `RuleVersion.change` carries `cause` (`stance_changed` / `text_changed` / `not_material`), the previous version and stance, and a bilingual `reason` written by the publisher (required for `text_changed`). Only `stance_changed` and `text_changed` suspend.
9. **Q-S5-3 (PO: yes):** a published rule version with a suspending cause moves `chosen` accounts to `pending_review` even before the user applies the new preset version to the account (S16 AC-3).
10. **Schema errors stay 400.** A fractional multiplier, a size with more than 2 decimals, a zero size or a blank name get 400 `common.invalid_request` with the pointer. The spec's `accounts.multiplier_invalid` is not needed: the UI maps the pointer.
11. **Profile size tie (Q60, provisional option c):** a real account copies the default of the nearest standard size. Distance is the absolute difference; below 25k the Core uses 25k, above 300k it uses 300k. On an exact tie the Core does not choose: `getNearestProfileSize` (S6) returns both candidates, and `createAccount` then requires `profile_size` (422 `accounts.profile_size_required` / `accounts.profile_size_invalid`). If the user decides (a) smaller or (b) larger, the candidate list has one entry and the contract does not change.
12. **3.0.0 review fixes (Crivo, 2.4.0):**
   - `updateAccount` requires `opt_ins.automation` only when that request changes the automation rule version; `copy` is never required there (S5-1).
   - `setAccountOptIn` is idempotent for the same choice and version (no step-up on the no-op).
   - `preset_attached` is reserved for a data-migration attach (Q41); no operation produces it.
   - `AccountUpdateRequest` mirrors the create rules: preset XOR manual, `size_amount` without a preset.
   - `SizeAmount` refuses zero by pattern.
   - Response schemas are deliberately looser than the data-model `CHECK`s; the Core never returns a row that breaks them.
   - Step-up (QA Security L1; superset pending the user with Q35): changing the binding of an account that receives automation needs action `account_binding_change` (target = account).
13. **Isolation:** another user's account or connection is indistinguishable from a non-existent one (404 `common.not_found`; 422 `accounts.platform_account_unknown`). `accounts.platform_account_taken` (409) is only ever about the caller's own accounts.

Q-S5-13: `accounts.platform_unbound` is a **routing** reason (an unbound account is not routable), not an S5 write error. It is defined with the S7 reason codes.

Check precedence (common order): 401 → 403 `common.forbidden_origin` → 400 → 404 → 403 step-up → 409 → 422. On create, an idempotent replay is answered before the step-up check.

## 4. Audit events emitted by S5 (category `config`)

These are the spec §13 codes, adopted:
- `accounts.created`, `accounts.updated`, `accounts.archived`: changed fields with old and new values, money as strings. `archived` lists the removed routes and links.
- `accounts.lifecycle_changed`: previous and new state, and whether a position was open.
- `accounts.opt_in_chosen`: kind, choice, previous choice, rule version, firm stance, source URLs and access dates of the text shown.
- `accounts.opt_in_suspended`: cause (`stance_changed` / `text_changed` / `preset_attached`), old and new rule version.

They are written in the same transaction as the change, through `app.outbox`. Their rendering and list format belong to the S10 contract.

## 5. Data-model deltas (for the Database Architect, through the Maestro)

1. `accounts.account.firm_name text` (prop, manual mode). `plan_name` / `phase` already exist. For prop accounts, `CHECK`: either `preset_version_id IS NOT NULL` or `firm_name`, `plan_name`, `phase` are all set.
2. `accounts.account.firm_platform text` (reserved in §5.2; now named).
3. `automation_pending_reason`, `copy_pending_reason text CHECK IN ('stance_changed','text_changed','preset_attached')`, set exactly when the state is `pending_review`.
4. `accounts.account.create_idempotency_key uuid` + `create_request_hash bytea`, with `UNIQUE (user_id, create_idempotency_key)`, never expiring. They are kept on the row, so no new table. The 24-h replay window is checked against `created_at`; after it, the key gets 409. Applied in data model rev. 8 (Lastro, 5dd2d45).
5. A rule-version catalog table must exist in S5, not only in S16, for the generic rule versions (one per kind): `catalog.opt_in_rule_version (id, kind, firm_stance, is_generic, firm_id NULL, preset_version_id NULL, firm_platform NULL, version_number, published_at, quotes jsonb, research jsonb, change_cause, change_reason jsonb, previous_id)`. Its exact shape is decided with S16. `automation_rule_version_id` / `copy_rule_version_id` reference it.
6. The `CHECK (kind = 'prop' OR …)` rule is unchanged. Real accounts stay `not_required` with no rule version.
